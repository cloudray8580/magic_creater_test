# ADR 0002｜采用小规模单应用架构

- 日期：2026-09-26
- 状态：**已接受：用户确认按本方案形成首版设计文档；尚未实现或部署**
- 依据：用户明确以小规模使用为主，希望避免过度设计，并要求可迁移到阿里云 ECS。
- 详细设计：[首版设计](../design/01-mvp-design.md)
- 相关历史：[ADR 0001](0001-proposed-direction.md)

## 背景

早期调研同时讨论了离线创作、班级服务、公开社区和多校部署，容易将未来能力误认为首版必需。用户澄清流量不会很高，以小规模使用为主，并关注技术成熟度、部署可迁移性与多游戏边界。

## 决定

1. 首版做带关卡编辑器和班级作品库的创作游戏，一种玩法支持多个学生作品。
2. TypeScript、React、Vite 用于网页开发；Phaser 是二维运行器的优先候选，经目标设备原型后确定是否保留及锁定版本。
3. 一个 Node.js / Fastify 应用同时提供网页和业务接口，SQLite 作为本机嵌入式数据库。
4. 固定学生/老师两种角色，采用简单班级作品列表、固定版本确认展示与反馈流程。
5. 本地草稿防丢、联网保存和文件导出进入首版；完整 PWA 和多设备离线自动合并推迟。
6. 首版使用内置素材与预定义玩法，Blockly、通用脚本执行、实时协作和开放社区推迟。
7. 应用使用可迁移的 Docker 镜像，数据独立持久化；11700 用于开发/内部试用，正式服务可部署 ECS 或学校批准的机器。
8. 对外 HTTPS 入口复用已有 Nginx，或选择 Caddy；不同时引入两套入口。
9. 不因预想流量引入微服务、独立缓存、消息队列或 Kubernetes；实际瓶颈出现后再扩展。

## 理由

- 当前核心风险是创作与反馈流程能否被使用，首版功能和运维规模应与之对应。
- 游戏在浏览器中运行，服务端主要保存作品及反馈；小规模单实例适合从 SQLite 起步。
- TypeScript 和一致的关卡格式有助于减少编辑、试玩、保存之间的数据错误。
- 同一应用提供网页和 API，减少独立部署、跨域和配置负担。
- Docker 与独立数据目录有助于迁移，但仍需数据备份、配置和恢复验证。
- 保留作品类型和数据版本足以为后续玩法扩展提供起点，不提前建设通用游戏平台。

## 代价与限制

- 单实例存在维护停机和主机故障风险；通过备份恢复承担当前规模的运维需求。
- SQLite 到 PostgreSQL 的升级不是零成本；数据库脚本及数据结构需要可追踪。
- 第二种玩法仍需开发对应编辑/运行逻辑，不能仅添加一条配置就自动得到新游戏。
- 目标设备、确切版本和性能尚未验证；TypeScript 不替代运行时校验。
- 技术方案不证明教育效果，也不代表公开发行或学校交付已经获得适用许可。

## 与旧记录的关系

本 ADR 取代早期材料中将“离线文件交换优先”视为唯一交付顺序的技术建议，确定小规模班级 Web 应用为当前设计方向。仅替代技术范围及实施顺序；不把 ADR 0001 中的年龄、医疗效果、活动方式或商业决策一并视为已确认。

历史调研保留，文档入口指向本 ADR 与设计页。年龄、具体目标学生、学校伙伴和正式发行渠道仍待明确。

## 重新评估条件

实际玩法更适合纯网页交互、3D 或原生客户端；首要渠道变为小游戏；需要多个应用实例；实测出现数据库写入瓶颈；或需要在完全断网条件下首次启动。出现具体条件后，通过新的 ADR 修改决定。
