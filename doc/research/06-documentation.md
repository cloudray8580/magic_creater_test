# 06｜项目文档、多人共享与 Agent 协作

日期：2026-09-26。结论：**保留仓库 `doc/`，同时选一个大家愿意使用的协作入口。** 两者承担不同编辑任务，每篇文档只有一个权威来源。

## 1. 是否全部只放 Markdown

对技术实现、正式规格、研究证据和决策，Markdown + Git 很适合：Agent 可直接读取、搜索和修改，变更可审查，可以与对应代码版本一起回滚。

对老师、心理顾问、设计者和其他不熟悉 Git 的伙伴，实时文档通常更容易参与：评论、共同写活动脚本、整理访谈、开会时改提纲。只允许提 PR 可能减少有效反馈。

推荐分工：

| 资料 | 权威位置 | 为什么 |
|---|---|---|
| 本轮调研、来源、正式需求和架构 | 仓库 `doc/` | 能审查、可复现、Agent 易使用 |
| 需求讨论、会议纪要、非敏感访谈总结 | 钉钉团队知识库/文档 | 多人共同编辑、评论、降低参与门槛 |
| 已通过的产品决定 | 仓库 `doc/decisions/`，协作文档放链接/摘要 | 让后来者知道为什么决定 |
| 开发任务、缺陷、验收状态 | GitHub Issues/Projects 或团队已有任务系统 | 有责任人、状态和代码关联 |
| 美术、声音等素材 | 受控文件存储 + 仓库内许可与索引 | 避免 Git 被大文件拖慢，保留版权来源 |
| 学生原始数据、录音、名册、心理问卷 | 学校或研究方批准的受限系统 | 普通私有 Git 仓库/团队文档不是默认合适的存储场所 |

目录名 `doc/` 和 `docs/` 没有本质技术差异；本项目按你提出的 `doc/` 使用，保持一致即可。

## 2. 平台比较

| 方案 | 人类协作 | Agent 使用 | 成本/限制 | 当前建议 |
|---|---|---|---|---|
| 私有 GitHub 仓库 Markdown | PR、评审、网页编辑；非实时同页协作 | 文件、Git、CLI/API 很直接 | 国内访问体验、成员熟悉程度；大文件不合适 | **正式文档首选** |
| 钉钉文档/知识库 | 中文团队、多端协作和评论方便 | 当前会话已有文档 MCP；另有官方 DWS CLI | 具体团队权限、额度和保留规则需看账户权益 | **已有钉钉团队时优先** |
| Notion | 页面、数据库、评论、跨文档组织 | 官方 MCP/API | 免费多人空间有区块等限制；本地访问条件需实测 | 团队已经使用时可选 |
| 飞书文档 | 文档/表格/知识库一体化 | 开放平台提供文档 API，需应用授权和适配 | 不应假定当前 Agent 已有读写权限；套餐另核 | 已用飞书则无需为了本项目换工具 |
| GitHub Wiki | 便于浏览，Git存储 | 可克隆独立 wiki 仓库 | 私有仓库 wiki 不是 GitHub Free 的通用免费能力 | 当前私有项目不优先 |
| 自托管 HedgeDoc | 实时协作 Markdown | 可用受控导出/文件或自行接 API | 认证、更新、备份、可用性由团队负责 | 有明确自托管需求再做 |
| VitePress 文档站 | 目录和检索体验好 | Markdown 仍可直接读 | 它是展示层，不是实时共同编辑器 | 文档规模增长后由 `doc/` 构建 |

依据：[DWS 官方开源 CLI](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli)、[Notion MCP](https://developers.notion.com/guides/mcp/overview)、[Notion 套餐](https://www.notion.com/pricing)、[飞书文档 API 入口](https://open.feishu.cn/document/server-docs/docs/docs-overview)、[GitHub Wiki 适用计划](https://docs.github.com/en/communities/documenting-your-project-with-wikis/about-wikis)、[HedgeDoc](https://github.com/hedgedoc/hedgedoc)、[VitePress](https://vitepress.dev/guide/what-is-vitepress)。

Notion 当前免费计划列出的页面历史为 7 天、单个附件上限 5 MB，多成员空间存在区块限制。这些是版本历史和容量限制，不是“正文只保存 7 天”。价格和权益会变化，本文不承诺长期不变。[官方价格页](https://www.notion.com/pricing)

## 3. 钉钉免费情况下到底保存多久

**本次没有查到可以支持“所有免费钉钉在线文档 X 天后会删”或“保证永久免费永久保存”的统一官方承诺，因此不编一个期限。**

官方产品页面支持免费使用和在线文档协作，能够确认产品提供这些能力；但“免费使用”不能推导为无限期、无限容量、无限历史版本和所有组织离职后继续可访问。[钉钉文档产品页](https://alidocs.dingtalk.com/product/doc)、[钉钉标准版介绍](https://home.dingtalk.com/)

需要分别问清六件事：

| 问题 | 实际含义 | 本次结论 |
|---|---|---|
| 文档正文保存多久 | 正在使用、未删除的文件会不会因时间失效 | 未核实统一固定期限，不能承诺永久 |
| 历史版本保留多久 | 能回到多早的旧内容 | 免费/付费、个人/组织和产品类型需看实际权益 |
| 回收站保留多久 | 删除后可以恢复的窗口 | 当前连接器说明写有 30 天；这不是正文寿命，也不是所有产品权益承诺 |
| 聊天附件多久有效 | 聊天发送文件的下载与缓存 | 不应套用到在线文档 |
| 空间额度与超限处理 | 能否继续上传/编辑、是否要扩容 | 看个人、组织存储和套餐 |
| 账号/组织变更后谁拥有 | 离职、解散组织、注销账号、权限变化 | 应指定团队所有者和交接机制 |

官方隐私政策采用实现服务目的所需期限、法定义务及账户状态等原则，也不能据此反推一个在线文档永久存储 SLA。[钉钉隐私政策](https://terms.alicdn.com/legal-agreement/terms/suit_bu1_dingtalk/suit_bu1_dingtalk202010070946_49604_15_5_18288.html)、[文档企业版隐私政策](https://terms.alicdn.com/legal-agreement/terms/privacy_policy_full/20240802170817913/20240802170817913.html)

检索到一些自称帮助中心的相似域名，以及标明 AI 生成的营销页面，声称“30 天/180 天/永久”。本报告没有把它们作为套餐承诺。真正决定长期归档方案之前，应在拟使用账号的权益页核验，或向官方客服取得针对“免费标准版、某种空间、某种文件类型”的明确答复。

**可立即采用的做法：** 把钉钉作为协作工作区；讨论形成正式结论后导出 Markdown/附件索引，进入 Git；重要资料另有受控备份。这样无需依赖一个尚未核实的永久存储承诺。

## 4. 当前 Agent 能使用钉钉文档吗

当前会话的工具清单已提供：搜索文档、读取 Markdown、创建/更新在线文档、导出 Markdown、历史版本以及权限查询等能力。这里只检查了工具能力，**没有读取私人文档，也没有验证本项目某个空间的权限或创建共享链接**。

官方开源 DWS CLI 也面向人和 AI Agent，能把文档、知识库与其他钉钉产品能力接入命令行。[DWS 仓库](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli)

“可被 Agent 使用”至少应满足：

1. 能在明确授权范围内搜索和读取正文，而不是只有截图。
2. 能按稳定文档 ID 找到同一对象，导出后保留来源链接和更新时间。
3. 修改前能读取最新内容，避免覆盖别人的编辑。
4. 能记录版本和变更原因，失败时可恢复。
5. 附件和表格有可用导出路径；不是只有摘要能被读取。

工具支持不等于你所有伙伴的 Agent 都自动拥有权限。需要使用正确账号和团队空间，为协作伙伴逐个授权，不默认公开到互联网。

## 5. 推荐目录结构

本轮已经创建研究与方向建议。其余目录按真实需求逐步增加：

```text
doc/
  README.md                 # 入口、文档状态、推荐阅读顺序
  research/                 # 有出处、有日期的事实与分析
  decisions/                # ADR：背景、选项、决定、后果
  product/                  # 目标人群、用户流程、范围、行为规则
  design/                   # 原型、视觉、交互与可访问性
  engineering/              # 架构、数据格式、接口、安全、部署
  pilots/                   # 活动方案、去标识总结、改进决定
  operations/               # 教师使用、备份恢复、审核处置
  assets/                   # 文档小图和素材许可索引
```

不要创建一堆长期空置的模板。每次产生真实决定或接口再新增对应文档；一页一个主问题，入口能找到所有有效资料。

## 6. 人类与 Agent 的更新流程

### 6.1 每篇文档声明元信息

建议字段：标题、状态（草案/待审/已确认/废弃）、负责人、最后核验日期、适用版本、权威位置、来源或关联议题。角色负责人未确定前标“待分配”，不要给不存在的人指派责任。

### 6.2 两条单向路径

- **讨论类：** 钉钉为主 → 人类审议 → Agent 导出/提炼 → 仓库新增正式记录。
- **规格类：** Git 为主 → PR 或显式评审 → 合并 → 钉钉入口更新摘要/链接。

不要让两端同时无条件覆盖相同正文。若需要同步，保存 `remoteDocumentId`、`lastRemoteUpdatedAt`、`lastExportedHash`、`repoPath`、`authority`；同步前比对远端和本地是否都变更。冲突时生成差异供审阅，不静默决定谁赢。

这些字段是建议的同步设计，当前没有运行自动同步程序。

### 6.3 可审计的研究记录

事实写来源；推断标为推断；未确认标为待核验；政策注明地区和检索日期；价格注明是否官方、统计期和计费条件。避免把宣传页的“有效”改写成临床结论。

## 7. 备份与访问

项目文档建议至少保有 Linux 工作副本、经过提交的 Git 远端和独立备份。远端私有不代替备份，也不代表可以放学生敏感资料。

协作文档由团队空间持有，至少有两位合适管理员，关键成员离开时交接；每个里程碑保存一次正文和必要附件。若使用自托管文档，明确谁维护升级、磁盘、证书、数据库备份与恢复。

本次只是提出工作流，没有建立定时任务、改变账号权限、在个人家用服务器上公开文档服务或创建钉钉组织。

## 8. 当前推荐

**现在就用仓库 `doc/` + 钉钉协作入口的组合。** 不急于自托管文档平台，也不必为了 Agent 另买一套系统。下一步在确认团队所在组织和成员以后，选一个专门项目知识库，把研究入口和待讨论问题放进去，Git 保留正式版本。
